# Plan-PRD Pattern: Markdown-Staged Planning Flow

> Источник: https://github.com/affaan-m/ECC (MIT) — `docs/PLAN-PRD-PATTERN.md`. Адаптировано для TT3Dato.

Лёгкий SDLC-ориентированный процесс планирования: каждая фаза жизненного цикла создаёт commit-able markdown **staging-файл**, который потребляет следующий шаг.

> Коротко: PRD -> план -> tdd-workflow -> PR. Каждая стрелка — файл на диске, а не состояние в памяти разговора.

## Staging-файлы

Каждый артефакт планирования — простой `.md`-файл:

```
Blueprint/
  prds/       # Product Requirements Documents
  plans/      # Implementation plans (использует агент Planner)
Workflows/
  reviews/    # Артефакты code review (использует CodeReviewer)
```

Свойства staging-файлов:

- **Plain markdown** — читается людьми, diff-ится в PR, ищется grep.
- **Committable** — коммитятся вместе с кодом/решением.
- **Composable** — каждая команда принимает файл предыдущей стадии как аргумент.
- **Resumable** — можно закрыть сессию, открыть новую и передать путь к файлу.

## Поток

```
[PRD: "проблема, для кого, критерии готовности"]
        |
        v
[План: файлы, паттерны, задачи, валидация]   <- агент Planner
        |
        v
[Реализация test-first]                       <- Skills/tdd-workflow
        |
        v
[Review + Delivery]                           <- CodeReviewer, commit/PR
```

Каждый блок — **gate (ворота)**. Можно останавливаться между gates, перезапускать с любого gate по пути файла, пропускать gates для мелких задач.

## Разделение PRD и плана

| Артефакт | Отвечает на вопрос | Фаза | Файл |
|---|---|---|---|
| PRD | «Какая проблема? Для кого? Как понять, что готово?» | Требования | `Blueprint/prds/{name}.prd.md` |
| План | «Какие файлы, паттерны и задачи удовлетворяют требованию?» | Дизайн + стратегия | `Blueprint/plans/{name}.plan.md` |

Почему не объединять:

- **Разделение ответственности**: PRD отвечает на «зачем», план — на «как».
- **Разные аудитории**: заинтересованное лицо не читает пути файлов; инженеру не нужен market-research.
- **Разный жизненный цикл**: PRD стабилен, план переписывается несколько раз.
- **Опциональность**: багфиксы и мелкие рефакторинги не требуют PRD.

## Когда что использовать

PRD — когда:

- объём неясен или оспаривается;
- несколько заинтересованных сторон должны согласовать проблему;
- изменение крупное, и зафиксировать гипотезу дешевле, чем пересматривать объём.

План напрямую — когда:

- требования уже ясны (баг-репорт, scoped-рефакторинг, известная миграция);
- работа малая, достаточно плана в разговоре + подтверждения;
- PRD уже есть — передай его в план.

## Почему staging-файлы лучше состояния в памяти

- **Переносимость**: путь PRD в новой сессии мгновенно восстанавливает контекст.
- **Аудируемость**: ревьюер видит намерение рядом с результатом.
- **Версионируемость**: файл эволюционирует в git-истории вместе с кодом.
- **Машинная разборчивость**: следующий шаг автоматически берёт следующий pending-milestone.

## Связь с агентами TT3Dato

- `Agents/Planner` — производит `Blueprint/plans/*.plan.md`;
- `Agents/CodeReviewer` — потребляет планы и производит `Workflows/reviews/*`;
- `Skills/tdd-workflow` — реализация test-first;
- Цикл соответствует Конституции, раздел 15 (plan -> test -> implement -> review -> verify -> remember -> improve).
