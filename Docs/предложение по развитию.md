# 1. Почему «много агентов — это плохо»? (примирение с саморазвитием)

## Исходная цель не отменяется

Ты хочешь, чтобы система **постоянно саморазвивалась и брала лучшее из разных репозиториев**. Это верно и остаётся в силе — это закреплено в Конституции (раздел 11 «Саморазвитие»).

## В чём была ошибка «серого кардинала»

Прежний план предлагал **вручную создавать агентов**: `Создай Researcher`, `Создай Auditor`, `Создай Critic`... Это и есть «плохо»:

- нарушает принцип **Open Source First** (мы пишем своё там, где уже есть готовое);
- каждый рукотворный агент требует память, инструменты, права, обновления и поддержку → **нагрузка растёт квадратично**, появляется «агент для агента для агента»;
- без проверки «а не умеет ли кто-то это уже делать лучше?» мы плодим **велосипеды**.

## Правильный механизм саморазвития

Саморазвитие выражается не в создании агентов, а в **курировании импорта**:

```
Agent Registry
  ↓
Repository Scanner (поиск в open source, в т.ч. через awesome-списки)
  ↓
Role Matching (какие роли/возможности закрывает)
  ↓
Compatibility Check (язык, лицензия, зрелость, зависимость)
  ↓
Proposal (объяснение + альтернативы)
  ↓
Approval (разрешение владельца)
  ↓
Import → Integration → Testing → Activation
```

**Агенты — это результат, а не отправная точка.** Система растёт, потому что **HuckleberryFinn** (один сильный агент) выполняет этот конвейер и подключает лучшее из мирового open source. Researcher/Auditor — **режимы работы** HuckleberryFinn, а не отдельные сущности.

**Ответ на вопрос:** «много агентов плохо» относится только к **самодельным** агентам. Развитие через **импорт зрелых компонентов** — ровно то, чего ты хотел изначально. Ограничитель — не «не расти», а «**сначала один проверенный вертикальный срез, потом расширение**».

## 2.2. Ruflo — методология исследований

- Сильное: workflow многоисточникового исследования (deep-research), построение досье (dossier-collect), структура агента.
- Уже взято: `Agents/Researcher`, `Agents/Auditor` (адаптированы из Ruflo).
- Не берём: тяжёлый MCP-сервер (323 инструмента), бинарный `agentdb.rvf`, полную установку.
- Дальше: **периодический пересмотр upstream** на предмет новых ролей/prompts.

## 2.3. ECC — цикл с памятью и skills

- Сильное: цикл `plan → test → implement → review → verify → remember → improve` (уже в Конституции, раздел 15); **Memory Vault `ecc.memory.v1`** (единый inspectable markdown-формат памяти); **281 навык**; **AgentShield** (аудит безопасности конфигов агентов); evidence-трейл; Plan Canvas.
- Берём: формат памяти `ecc.memory.v1` как стандарт `Memory/`; структуру папки `skills/` и избранные навыки (TDD, security review, deep research); концепцию AgentShield → в `Docs/Audits/Agent_Config_Security_Checklist.md`; требование «evidence trail» к отчётам аудита.
- Не берём: ECC Pro (платно), JavaScript-код, полную установку.

## 2.4. OmniRoute — экономика LLM

- Сильное: один endpoint к ~290 провайдерам, ~1,53 млрд бесплатных токенов/мес, 19 стратегий маршрутизации, сжатие контекста RTK+Caveman (~89% экономии).
- Применимо: когда TT3Dato начнёт массово гонять LLM (аудит, исследование, генерация) — подключить как **внешний шлюз**, не в ядро.
- Статус: **CANDIDATE / MONITORING**, внедрять после MVP.
- Сейчас: зарегистрировать в OpenSourceRegistry, не интегрировать.

## 2.5. Aegis — безопасность и верифицируемая память

- Сильное: **trust-домены** (изоляция данных), **верифицируемая память** (unverified → verified), **карантин ввода** (защита от prompt injection), **бюджет как контракт**.
- Берём (концепции, не код): trust-домены → изоляция данных клиентов в `clients/<slug>/`; верифицируемую память → усиление принципа Конституции «истина хранится внутри TT3Dato»; карантин ввода → обязательная валидация внешних данных/сообщений; бюджет как контракт → контроль расходов на LLM и исследования.
- Не берём: ранний код (2 звезды, 8 коммитов) — пока нестабилен. Наблюдаем.

## 2.6. awesome (sindresorhus) — мета-каталог

- Что это: **эталонный каталог кураторов** — сотни тематических списков, каждый с критериями качества, лицензия CC0, приём контрибуций через PR.
- Что берём (это ключевой вывод):
  1. **Методология курирования** — именно по ней строим свой `OpenSourceRegistry.md`: категории, статусы, критерии отбора, обязательные поля (что умеет, какие роли закрывает, язык, лицензия, последний коммит, зрелость, совместимость, статус). Правила из `create-list.md` переиспользуем как критерии оценки кандидатов.
  2. **Источники для поиска** — релевантные разделы awesome становятся «полками» для сканирования: AI agents, self-hosted, RAG / LLM, automation, databases, security (в т.ч. prompt injection, AgentShield-тема), Claude Code / Gemini CLI, ChatGPT, bots.
  3. **Модель контрибуций** — PR с критериями, соответствует нашему Decision/Approval Protocol.
  4. **Инструменты-указатели** (Related): awesome-search / awesome-cli — будущие инструменты поиска по нашему реестру.
- Не берём: сам список целиком (95% нерелевантно нашей нише).

# 3. Вывод: что стянуть в TT3Dato

## 3.1. Приоритет 1 — OpenSourceRegistry.md (сейчас)

Создать `Docs/OpenSourceRegistry.md` — «энциклопедию» решений по методологии awesome-листов:

- Поля записи: **Repository · Что умеет · Какие роли закрывает · Язык · Лицензия · Последний коммит · Зрелость · Совместимость · Статус (USED / CANDIDATE / MONITORING / REJECTED)**.
- Начать с уже известного: Ruflo (USED), ECC (USED — методология), OmniRoute (CANDIDATE), Aegis (MONITORING), awesome (USED — методология курирования).
- Сканировать релевантные awesome-разделы для наполнения (агенты, память/RAG, self-hosted, безопасность).
- Это ценнее десятка самодельных агентов и фундамент для конвейера импорта.

## 3.2. Приоритет 2 — память и навыки из ECC

- Закрепить **`ecc.memory.v1`** как стандарт `Memory/` (уже частично есть).
- Сформировать папку **`Skills/`**: адаптировать избранные навыки ECC (TDD, security review, deep research).
- Применять **evidence-трейл** к отчётам аудита (доказательства по каждому утверждению).

## 3.3. Приоритет 3 — безопасность из Aegis (концепции)

- Изоляция данных клиентов: `clients/<slug>/` как trust-домен, без перекрёстного доступа.
- Карантин ввода: валидация всех внешних сообщений/файлов (клиентский бот, inbox, MCP).
- Верифицируемая память: unverified → verified уже в политике памяти.
- Бюджет как контракт: зафиксировать лимиты на исследования/LLM.
- Внести в `Docs/Audits/Agent_Config_Security_Checklist.md` + Agent Registry.

## 3.4. Приоритет 4 — Ruflo (поддержка) и OmniRoute (отложенно)

- Ruflo: периодический пересмотр upstream, обновление Researcher/Auditor prompts.
- OmniRoute: зарегистрировать в OpenSourceRegistry; интеграцию — **после MVP** для экономии на массовых LLM-операциях.

## 3.5. Что НЕ берём

- Полный Ruflo (MCP, agentdb.rvf).
- ECC Pro (платный), JavaScript-код ECC.
- OmniRoute сейчас (инфраструктура + настройка).
- Код Aegis сейчас (ранний MVP).
- Весь awesome-список целиком.
- Любые самодельные агенты до прохождения конвейера Registry.

# 5. Критерий успеха

После внедрения шага 1–4 система должна:

- иметь **энциклопедию open source** с обоснованными статусами;
- развиваться по конвейеру «Registry → Scanner → Matching → Compatibility → Proposal → Approval → Import → Testing → Activation»;
- не иметь ни одного самодельного агента, созданного без проверки готовых решений;
- выполнять вертикальный срез: задача → исследование → аудит → предложение → разрешение → изменение в Git.
