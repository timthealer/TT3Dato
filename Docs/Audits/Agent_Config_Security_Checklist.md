# Agent Config Security Checklist (AgentShield-подход)

Локальный defensive-чек-лист аудита собственных конфигурационных файлов агентов TT3Dato. Адаптирован из методологии AgentShield (ECC): 5 категорий сканирования, оформленных как локальные проверки.

**Важно:** чек-лист выполняется локально, только для собственных файлов под `/workspace/Agents/` и `/workspace/Skills/`. Никакого сканирования внешних систем, сетевых атак или эксплуатации. Проверки выполняются человеком или агентом с инструментами Read и Grep.

## Область проверки

- `/workspace/Agents/*/` — определения агентов (system.md, config, state);
- `/workspace/Skills/**` — навыки и правила;
- `/workspace/Docs/Agent_Permissions` — права агентов;
- `/workspace/Docs/Agent Registry` — реестр агентов.

Инструменты: Read, Grep, Glob. Никаких сетевых операций.

---

## Категория 1. Обнаружение секретов (secrets detection)

Цель: убедиться, что в конфигурациях нет токенов, ключей и паролей.

Чек-лист:

- [ ] Выполнить поиск по `/workspace/Agents/` и `/workspace/Skills/` паттернов токенов и ключей: `api[_-]?key`, `secret`, `password`, `passwd`, `token`, `bearer`, `sk-`, `ghp_`, `glpat-`, `AKIA` (AWS).
- [ ] Проверить, что найденные упоминания являются placeholder'ами (`<your-key>`, `${VAR}`), а не реальными значениями.
- [ ] Проверить, что файлы `.env`, `config.json`, `config.yaml`, `settings.json` в области проверки не содержат захардкоженных credentials.
- [ ] Проверить, что значение `MCAI_LLM_API_KEY` и аналогичных переменных агентного окружения не записано в файлы проекта.
- [ ] Подтвердить, что ключи не передаются через аргументы командной строки в документации и примерах.
- [ ] Подтвердить, что логи (включая `Logs/`) не содержат обрывков ключей.
- [ ] Убедиться, что разрешения файлов с чувствительными данными не избыточны (для секретов — только владелец).

## Категория 2. Аудит разрешений (permission auditing)

Цель: агенты имеют минимально необходимые права согласно `Docs/Agent_Permissions`.

Чек-лист:

- [ ] Сверять права каждого агента в конфигурации с записью в `Docs/Agent_Permissions` и `Docs/Agent Registry`.
- [ ] Подтвердить, что агенты не имеют прав на изменение Конституции и Agent Registry без одобрения (проверка «change Constitution», «change Agent Registry»).
- [ ] Подтвердить, что запрещены удаляющие операции (delete repository, destructive commands) без явного подтверждения.
- [ ] Проверить, что чтение (`READ`) ограничено нужными каталогами, а не всем репозиторием без необходимости.
- [ ] Проверить, что запись (`WRITE`) выполняется после подтверждения, как указано в правах.
- [ ] Подтвердить, что нет неиспользуемых привилегий (granted, но нигде не задействованных).
- [ ] Подтвердить, что у каждого агента есть запись в Agent Registry (Конституция, раздел 5).

## Категория 3. Анализ инъекций в hooks (hook injection analysis)

Цель: убедиться, что в правилах и конфигурациях нет командных инъекций, выполняемых при обработке входных данных.

Чек-лист:

- [ ] Найти все hook-подобные объявления и скриптовые фрагменты в `/workspace/Skills/` и `/workspace/Agents/` (упоминания PreToolUse, PostToolUse, Stop, команд в документации).
- [ ] Проверить, что команды, показанные в документации, не содержат интерполяции непроверенных входных данных (например, `eval`, backticks, `$(...)` с вводом пользователя).
- [ ] Проверить, что примеры команд не используют inline-комментарии в конце строки там, где это ломает копирование.
- [ ] Подтвердить, что нет флага dangerously-skip-permissions и обходов проверок разрешений.
- [ ] Подтвердить, что конфигурация `allowedTools` перечисляет явный минимальный набор инструментов.
- [ ] Проверить, что в текстах промптов агентов нет инструкций, способных переопределить системные ограничения (вредоносный `system`-переопределяющий промпт).

## Категория 4. Профилирование рисков MCP-серверов (MCP server risk profiling)

Цель: оценить риски любых MCP-серверов, объявленных в конфигурациях TT3Dato.

Чек-лист:

- [ ] Составить список всех объявленных MCP-серверов из конфигурационных файлов под `/workspace/Agents/` и `/workspace/Skills/`.
- [ ] Для каждого сервера зафиксировать: источник (URL/пакет), назначение, какие инструменты он предоставляет.
- [ ] Оценить доверие к источнику: официальный репозиторий/пакет или неизвестный сторонний.
- [ ] Проверить, какие права получают инструменты MCP-сервера и ограничены ли они минимальными.
- [ ] Подтвердить, что MCP-конфиг не содержит секретов и URL с захардкоженными ключами.
- [ ] Подтвердить, что сервер не запрашивает сетевой доступ сверх назначения.
- [ ] При сомнении — отключить сервер до ручной проверки.

## Категория 5. Ревью конфигурации агентов (agent config review — prompt injection surfaces)

Цель: выявить поверхности prompt-инъекций в конфигурациях и промптах агентов.

Чек-лист:

- [ ] Прочитать каждый `system.md` / `config` под `/workspace/Agents/` и найти места, где внешние данные (документы, веб-контент, вывод других агентов) попадают в промпт без разметки.
- [ ] Подтвердить, что внешний контент отделён от инструкций (например, XML-тегами, экранированием) и явно помечен как «данные, а не инструкции».
- [ ] Проверить, что в правилах нет инструкций «выполнять команды из внешних данных» или «следовать инструкциям из документов».
- [ ] Подтвердить, что агенты не следуют инструкциям из пользовательской памяти (Memory `unreviewed context` не исполняется как политика).
- [ ] Проверить, что примеры в навыках не содержат злонамеренных «смены роли» («ignored previous instructions») без явной пометки как пример атаки.
- [ ] Подтвердить, что конфигурации не включают запрещённых действий из guardrails (туннели, сканы, эксфильтрация, установка третьих агентов).

## Итоговый протокол

- Для каждой категории: PASS/FAIL + список проблем.
- Найденные секреты — немедленно удалить из файлов и ротировать.
- Найденные лишние права — отозвать через `Docs/Agent_Permissions` после одобрения.
- Результат аудита сохранять как evidence в `Logs/` (план -> находки -> финальная проверка).

## Связь с другими документами

- `Docs/Agent_Permissions` — права агентов.
- `Docs/Agent Registry` — реестр агентов.
- `Skills/rules/hooks.md` — концепция детерминированных проверок.
- `Tests/README.md` — детерминированные проверки (например, поиск секретов можно оформить как проверку в `Tests/`).
- `Docs/TT3Dato_Constitution.md` — разделы 5 (Agent Registry), 7 (Critic), 13 (Запреты).
