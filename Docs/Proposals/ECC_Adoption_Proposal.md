**Основание:** `Docs/Research/ECC_Analysis.md` (разделы 3.1–3.3)
**Решение пользователя (ранее):** цикл ECC уже внесён в Конституцию (раздел 15); библиотеки ECC НЕ устанавливаются.
**Статус:** Ожидает решения пользователя (Decision Protocol, Конституция раздел 6)

---

# 1. Принцип переноса

- Переносим только **файлы методологии** (markdown: skills, agents, rules, workflow-стандарты) — НЕ устанавливаем npm-пакеты, плагины, харнесс-код ECC.
- Каждый перенесённый файл **адаптируется** под структуру TT3Dato (русские заголовки, ссылки на наши директории) и получает **атрибуцию** (источник `affaan-m/ECC`, MIT).
- Цель — «взять лучшее, не тащить зависимость» (Конституция, разделы 2, 4, 10).

# 2. Предлагаемый объём изменений

## Кластер 1. Skills (методологии) — в `Skills/`

Скопировать и адаптировать SKILL.md из ECC:

| Skill (ECC) | Адаптация для TT3Dato |
|---|---|
| `tdd-workflow` | Тест-ориентированный процесс для задач разработки TT3Dato |
| `deep-research` | Усиление процесса Researcher (многоисточниковый поиск) |
| `security-review` | Проверка безопасности агентных конфигов и внешних данных |
| `context-budget` | Контроль расхода контекста/токенов в длинных сессиях |
| `unified-memory` | Стандарт памяти между агентами (формат `ecc.memory.v1`) |
| `search-first` | Принцип «сначала поиск», замена гаданий фактами |
| `cost-aware-llm-pipeline` | Экономия токенов (согласуется с кандидатом OmniRoute) |
| `documentation-lookup` | Поиск по документации до написания кода |
| `agent-eval` / `agent-self-evaluation` | Оценка работы агентов TT3Dato |
| `market-research` | Исследование рынка/компаний — прямо в миссию TT3Dato |
| `parallel-execution-optimizer` | Параллельное выполнение задач (ускоряет аудит) |
| `agent-harness-construction` | Строительство агентных харнессов (наши агенты) |

Формат результата: `Skills/<name>/SKILL.md` + при необходимости `references/`, `templates/`.

## Кластер 2. Agents — в `Agents/`

Скопировать и адаптировать агентов ECC, закрывающих роли TT3Dato:

| Agent (ECC) | Роль в TT3Dato | Статус в реестре |
|---|---|---|
| `code-reviewer` | Critic (критический анализ кода/решений) | PLANNED -> усиление |
| `planner` | Планирование задач и решений | PLANNED |
| `code-explorer` | Repository Analyst (анализ кодовой базы) | PLANNED |
| `doc-updater` | Documentation Manager | PLANNED |
| `chief-of-staff` | Координация задач между агентами | PLANNED |
| `agent-evaluator` | Оценка качества агентов TT3Dato | PLANNED |
| `database-reviewer` | Аудит БД (для досье компаний) | PLANNED |

Каждый агент оформляется по нашему шаблону (`system.md`, `config.yaml`, `state.json`) и регистрируется в `Docs/Agent Registry`.

## Кластер 3. Rules (стандарты) — в `Docs/` или `Skills/rules/`

Скопировать и адаптировать селективные пакеты правил:

| Rules (ECC) | Применение |
|---|---|
| `rules/common/agents.md` | Стандарты описания агентов |
| `rules/common/code-review.md` | Стандарты критического анализа |
| `rules/common/coding-style.md` | Единый стиль кода |
| `rules/common/development-workflow.md` | Рабочий процесс (цикл ECC) |
| `rules/common/git-workflow.md` | Git-процедуры |
| `rules/common/hooks.md` | Событийные проверки |

Принцип ECC: rules всегда загружены, но ставить выборочно.

## Кластер 4. Memory Vault — в `Memory/`

- Внедрить формат `ecc.memory.v1` (Markdown) как стандарт памяти TT3Dato.
- Создать шаблоны: проектная память (`Memory/`), пользовательская память.
- Инструкции для агентов: память — «unreviewed context», не исполнимая политика; принятые знания продвигаются в документы (Конституция, раздел 9).

## Кластер 5. Evidence trail + Hooks-концепция — в `Logs/` и `Tests/`

- Стандарт «следа доказательств»: план + падающий тест + прошедший тест + находки ревью + финальная проверка — каждый результат агента сопровождается evidence.
- Концепция «детерминированных проверок вне промпта»: оформить как workflow-проверки в `Tests/` (по аналогии с hooks, но без харнесс-кода).

## Кластер 6. AgentShield-подход — как workflow (локально)

- НЕ устанавливаем `ecc-agentshield` (npm).
- Переносим методологию: чек-лист сканирования конфигов агентов на секреты, permission-аудит, hook-инъекции, MCP-риски (5 категорий).
- Оформляем как `Docs/Audits/Agent_Config_Security_Checklist.md` — локальная проверка собственных конфигов (defensive, без сетевых атак).

# 3. Варианты объёма (Decision Protocol)

## Вариант A — Полный перенос (рекомендуется)

Все 6 кластеров: 12 skills, 7 агентов, 6 пакетов правил, Memory Vault, evidence trail, security checklist.

- Плюсы: максимально закрываем методологии ECC; TT3Dato получает готовые процессы; все роли из реестра закрываются.
- Минусы: большой объём (30+ файлов), требуется адаптация каждого; растёт объём репозитория.

## Вариант B — Ядро (минимальный набор)

Кластеры 1, 3, 4: 12 skills + 6 пакетов правил + Memory Vault. Агентов добавлять по мере задач.

- Плюсы: методологии сразу, агентов — точечно; меньше адаптации.
- Минусы: роли Critic/Auditor усиление откладывается.

## Вариант C — Отложить

Зафиксировать кластеры в `Docs/Roadmap.md` как «Исследование», не копировать сейчас.

- Плюсы: ноль изменений, репозиторий остаётся минимальным.
- Минусы: не перенимаем проверенное решение (противоречит Конституции, раздел 2 «НЕ ИЗОБРЕТАТЬ ВЕЛОСИПЕД»).

# 4. Лицензия и атрибуция

- ECC распространяется под MIT — копирование и адаптация разрешены с сохранением уведомления.
- В каждый перенесённый файл добавляется блок: источник `https://github.com/affaan-m/ECC`, лицензия MIT.
- Создаётся `Docs/ATTRIBUTIONS.md` со списком всех заимствований.

# 5. Последствия

- Копирование файлов методологии не влияет на работающий код TT3Dato (репозиторий — конфигурация, код не исполняется).
- После переноса вновь подключённые агенты регистрируются в `Docs/Agent Registry`.
- Все изменения будут закоммичены отдельно после твоего подтверждения.
