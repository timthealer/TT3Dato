# Logs — Evidence Trail (процессные следы)

Каталог `/workspace/Logs/` — хранилище процессных следов работы агентов TT3Dato. Вместе с `Tests/` реализует стандарт «следа доказательств» (evidence trail), адаптированный из цикла ECC `plan -> test -> implement -> review -> verify -> remember -> improve` (Конституция, раздел 15).

## Что здесь хранится

Процессные логи — это запись того, как выполнялась задача: какие шаги пройдены, какие решения приняты, какие находки получены. Примеры:

- Планы реализации задач;
- Отчёты о выполненной работе агентов;
- Результаты ревью (находки code-reviewer / Auditor);
- Отчёты исследований (Researcher);
- Следы аудитов компаний;
- Журналы принятых архитектурных решений.

## Правило evidence trail

Каждый результат агента должен сопровождаться evidence:

1. **План** — что собирались сделать;
2. **Падающий тест** — подтверждение, что проблема существует;
3. **Прошедший тест** — подтверждение, что проблема решена;
4. **Находки ревью** — что выявил критический анализ (Critic Protocol);
5. **Финальная проверка** — подтверждение корректности (verify).

Результат — не только код или документ, а вся цепочка доказательств.

## Отличие Logs/ от Tests/

| Каталог | Назначение | Формат |
|---|---|---|
| `Logs/` | Процессные следы: планы, отчёты, ревью, решения | Свободный Markdown, по задаче |
| `Tests/` | Детерминированные проверки вне контекста модели | Исполняемые/воспроизводимые проверки, см. `Tests/README.md` |

`Logs/` отвечает на вопрос «как мы это делали», `Tests/` — на вопрос «как подтвердить, что это работает».

## Правила ведения

- Каждый значимый результат сопровождается записью-следом.
- Имя файла отражает задачу и дату: `<YYYY-MM-DD>-<task-slug>.md`.
- Логи не удалять: устаревшие помечать как историю.
- Актуальные правила и процедуры продвигать в governed-документы (Конституция, раздел 9), лог остаётся следом.
