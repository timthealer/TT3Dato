# Оптимизатор параллельного выполнения

Используйте этот skill, когда скорость достигается выполнением независимой работы одновременно: осмотр репозитория, чтение файлов, проверки API, проверки браузера, линии сборки/тестов, deploy readback или проходы реализации по нескольким worktree.

## Основной паттерн

Превращайте срочность в граф зависимостей перед действием.

1. Определите цель и сигнал готовности (done signal).
2. Разделите работу на линии (lanes).
3. Пометьте каждую линию как параллельную, последовательную или gated.
4. Запускайте независимые чтения/проверки вместе.
5. Держите записи изолированными по файлу, worktree, ветке, сервису или набору данных.
6. Сливайте только после того, как доказательства покажут, что линии совместимы.
7. Завершайте таблицей проверки, а не расплывчатым заявлением о скорости.

## Матрица линий

Перед большим рывком составьте компактную матрицу:

```text
Lane | Can run in parallel? | Write surface | Risk | Verification
Repo scan | yes | none | low | rg/git status outputs
Backend patch | maybe | src/api | medium | unit tests
Frontend patch | maybe | app/components | medium | browser screenshot
Deploy readback | after build | remote service | high | live URL + logs
```

Запускайте линии параллельно только тогда, когда их поверхности записи не сталкиваются.

## Правила выполнения

- Пакетно выполняйте чтения файлов, поиски, проверки статуса и запросы метаданных.
- Используйте изолированные worktree для больших несвязанных линий реализации.
- Запускайте длительные тесты, сборки, backfill'ы и деплои в отдельных сессиях, затем опрашивайте их осознанно.
- Если линия обнаруживает блокер, меняющий план, приостановите зависимые линии и обновите матрицу.
- Никогда не позволяйте фоновому процессу пережить ход, если только пользователь явно не запросил продолжающийся сервис.
- Не распараллеливайте разрушительные команды, миграции, записи в одну таблицу или живые деплои, влияющие на клиентов, без явного gate.

## Форма вывода

Используйте её при отчёте:

```text
Parallel execution result:
- Lanes run: 5
- Lanes completed: 4
- Blocked lane: deploy readback, waiting on DNS propagation
- Fast path found: batched repo scan + focused tests
- Verification: lint pass, unit pass, live smoke pass
```

## Режимы отказа

- Больше конкурентности, чем создаёт конфликтующие правки.
- Бенчмаркинг инструмента вместо задачи.
- Отношение к "быстро" как к готовности до доказательства корректности.
- Забывание опрашивать запущенные сессии.
- Скрытие пропущенных проверок за сводкой успеха.
