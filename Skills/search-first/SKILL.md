# /search-first — Исследуй перед тем, как писать код

Систематизирует рабочий процесс "ищи существующие решения перед реализацией".

## Триггер

Используйте этот skill, когда:
- Начинаете новую функцию, для которой, вероятно, уже существуют решения
- Добавляете зависимость или интеграцию
- Пользователь просит "добавить функциональность X", и вы собираетесь писать код
- Перед созданием новой утилиты, хелпера или абстракции

## Рабочий процесс

```
┌─────────────────────────────────────────────┐
│  0. PREFLIGHT ДОСТУПНОСТИ ИНСТРУМЕНТОВ      │
│     Проверьте каналы поиска перед тем, как   │
│     на них полагаться; честно сообщайте о    │
│     пропущенных каналах                       │
├─────────────────────────────────────────────┤
│  1. АНАЛИЗ ПОТРЕБНОСТИ                      │
│     Определите, какая функциональность нужна │
│     Определите ограничения языка/фреймворка  │
├─────────────────────────────────────────────┤
│  2. ПАРАЛЛЕЛЬНЫЙ ПОИСК (агент-исследователь)│
│     ┌──────────┐ ┌──────────┐ ┌──────────┐  │
│     │  npm /   │ │  MCP /   │ │  GitHub / │  │
│     │  PyPI    │ │  Skills  │ │  Web      │  │
│     └──────────┘ └──────────┘ └──────────┘  │
├─────────────────────────────────────────────┤
│  3. ОЦЕНКА                                 │
│     Оцените кандидатов (функциональность,   │

├─────────────────────────────────────────────┤
│  4. РЕШЕНИЕ                                 │
│     ┌─────────┐  ┌──────────┐  ┌─────────┐  │
│     │  Adopt  │  │  Extend  │  │  Build   │  │

│  5. РЕАЛИЗАЦИЯ                              │
```

## Матрица решений

| Сигнал | Действие |
|--------|----------|
| Точное совпадение, хорошо поддерживается, MIT/Apache | **Adopt** — установить и использовать напрямую |
| Частичное совпадение, хорошая основа | **Extend** — установить + написать тонкую обёртку |
| Несколько слабых совпадений | **Compose** — скомбинировать 2-3 небольших пакета |
| Ничего подходящего не найдено | **Build** — писать собственное, но информированно через исследование |

## Как использовать

### Шаг 0: Preflight доступности инструментов

Это руководство для агента, а не исполняемый скрипт настройки. Проверяйте только каналы, релевантные текущей задаче и проекту.

| Канал | Проверка | Если отсутствует |
|---------|------------|------------------|
| Поиск по репозиторию | `rg --files` и целевые запросы `rg` | Укажите, что проверены только видимые файлы |
| Реестр пакетов | `npm --version`, `python -m pip --version` или package manager проекта | Используйте веб/документационный поиск и не заявляйте о покрытии реестра |
| GitHub CLI | `gh auth status` | Используйте только публичный веб или локальную историю git |
| MCP/документационные инструменты | Доступный список инструментов или локальная конфигурация MCP | Вернитесь к официальным docs/веб-поиску |
| Каталог skills | `ls Skills/` (каталог TT3Dato) | Скажите, что локальный каталог skills недоступен |

### Быстрый режим (inline)

Прежде чем писать утилиту или добавлять функциональность, мысленно пройдитесь:

0. Это уже существует в репозитории? → сначала `rg` по релевантным модулям/тестам
1. Это распространённая проблема? → поищите в npm/PyPI
2. Есть ли MCP для этого? → проверьте конфигурацию MCP TT3Dato и поищите
3. Есть ли skill для этого? → проверьте `Skills/` TT3Dato
4. Есть ли реализация/шаблон на GitHub? → запустите поиск кода GitHub по поддерживаемым OSS перед написанием нового кода

### Полный режим (агент)

Для нетривиальной функциональности запустите агента-исследователя:

```
Agent(subagent_type="general-purpose", prompt="
  Research existing tools for: [DESCRIPTION]
  Language/framework: [LANG]
  Constraints: [ANY]

  Search: npm/PyPI, MCP servers, TT3Dato skills, GitHub
  Return: Structured comparison with recommendation
")
```

Старые версии документации могут называть это `Task(...)`; используйте текущее имя инструмента agent/subagent, доступное в вашем агенте TT3Dato.

## Быстрые поисковые сокращения по категориям

### Инструменты разработки
- Linting → `eslint`, `ruff`, `textlint`, `markdownlint`
- Formatting → `prettier`, `black`, `gofmt`
- Testing → `jest`, `pytest`, `go test`
- Pre-commit → `husky`, `lint-staged`, `pre-commit`

### AI/LLM интеграция
- Claude SDK → Context7 для актуальных docs
- Управление промптами → проверьте MCP-серверы
- Обработка документов → `unstructured`, `pdfplumber`, `mammoth`

### Данные и API
- HTTP-клиенты → `httpx` (Python), `ky`/`undici` (Node)
- Валидация → `zod` (TS), `pydantic` (Python)
- База данных → сначала проверьте MCP-серверы

### Контент и публикация
- Обработка Markdown → `remark`, `unified`, `markdown-it`
- Оптимизация изображений → `sharp`, `imagemin`

## Точки интеграции

### С агентом-планировщиком
Планировщик должен вызывать исследователя перед Фазой 1 (Architecture Review):
- Исследователь выявляет доступные инструменты
- Планировщик включает их в план реализации
- Избегает "изобретения велосипеда" в плане

### С агентом-архитектором
Архитектор должен консультироваться у исследователя для:
- Решений о технологическом стеке
- Обнаружения паттернов интеграции
- Существующих референс-архитектур

### С skill итеративного поиска
Комбинируйте для прогрессивного обнаружения:
- Цикл 1: Широкий поиск (npm, PyPI, MCP)
- Цикл 2: Детальная оценка лучших кандидатов
- Цикл 3: Проверка совместимости с ограничениями проекта

## Примеры

### Пример 1: "Добавить проверку битых ссылок"
```
Потребность: Проверить markdown-файлы на битые ссылки
Поиск: npm "markdown dead link checker"
Найдено: textlint-rule-no-dead-link (оценка: 9/10)
Действие: ADOPT — npm install textlint-rule-no-dead-link
Результат: Ноль собственного кода, проверенное в бою решение
```

### Пример 2: "Добавить HTTP-клиент-обёртку"
```
Потребность: Устойчивый HTTP-клиент с ретраями и таймаутами
Поиск: npm "http client retry", PyPI "httpx retry"
Найдено: got (Node) с плагином retry, httpx (Python) со встроенным retry
Действие: ADOPT — использовать got/httpx напрямую с конфигурацией retry
Результат: Ноль собственного кода, проверенные в продакшене библиотеки
```

### Пример 3: "Добавить линтер файлов конфигурации"
```
Потребность: Валидировать файлы конфигурации проекта по схеме
Поиск: npm "config linter schema", "json schema validator cli"
Найдено: ajv-cli (оценка: 8/10)
Действие: ADOPT + EXTEND — установить ajv-cli, написать специфичную для проекта схему
Результат: 1 пакет + 1 файл схемы, без собственной логики валидации
```

## Анти-паттерны

- **Прыжок в код**: написание утилиты без проверки, существует ли она
- **Игнорирование MCP**: не проверка, предоставляет ли MCP-сервер уже эту возможность
- **Молчаливый пропуск**: сообщение "ничего не найдено", когда канал поиска был недоступен
- **Чрезмерная кастомизация**: оборачивание библиотеки так тяжело, что теряются её преимущества
- **Раздувание зависимостей**: установка огромного пакета ради одной маленькой функции
