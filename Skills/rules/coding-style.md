# Стиль кода

## Иммутабельность (CRITICAL)

Всегда создавать новые объекты, никогда не мутировать существующие:

```
// Псевдокод
НЕВЕРНО: modify(original, field, value) — изменяет original на месте
ВЕРНО:   update(original, field, value) — возвращает новую копию с изменением
```

Обоснование: immutable-данные предотвращают скрытые побочные эффекты, упрощают отладку и позволяют безопасный параллелизм.

## Основные принципы

### KISS (Keep It Simple)

- Предпочитать самое простое решение, которое реально работает;
- Избегать преждевременной оптимизации;
- Оптимизировать под ясность, а не под хитрость.

### DRY (Don't Repeat Yourself)

- Выносить повторяющуюся логику в общие функции или утилиты;
- Избегать расхождения копи-паст-реализаций;
- Вводить абстракции, когда повторение реальное, а не спекулятивное.

### YAGNI (You Aren't Gonna Need It)

- Не строить фичи или абстракции до того, как они понадобятся;
- Избегать спекулятивной обобщённости;
- Начинать просто, рефакторить, когда появляется реальная потребность.

## Организация файлов

МНОГО МАЛЕНЬКИХ ФАЙЛОВ > НЕСКОЛЬКО БОЛЬШИХ:

- Высокая связность, низкое сцепление;
- 200–400 строк типично, максимум 800;
- Выделять утилиты из крупных модулей;
- Организовывать по фичам/доменам, а не по типам.

## Обработка ошибок

Всегда обрабатывать ошибки комплексно:

- Явно обрабатывать ошибки на каждом уровне;
- Давать понятные сообщения об ошибках в UI-коде;
- Логировать детальный контекст ошибки на стороне сервера;
- Никогда не глотать ошибки молча.

## Валидация входных данных

Всегда валидировать на границах системы:

- Валидировать весь пользовательский ввод до обработки;
- Использовать schema-валидацию, где доступно;
- Отказывать быстро (fail fast) с ясными сообщениями;
- Никогда не доверять внешним данным (API-ответы, пользовательский ввод, содержимое файлов).

## Соглашения об именах

- Переменные и функции: `camelCase` с описательными именами;
- Булевы: предпочитать префиксы `is`, `has`, `should` или `can`;
- Интерфейсы, типы и компоненты: `PascalCase`;
- Константы: `UPPER_SNAKE_CASE`;
- Custom hooks: `camelCase` с префиксом `use`.

## Code Smells, которых избегать

### Глубокая вложенность

Предпочитать early returns вложенным условным блокам, когда логика начинает накапливаться.

### Магические числа

Использовать именованные константы для значимых порогов, задержек и лимитов.

### Длинные функции

Разбивать большие функции на сфокусированные части с ясными обязанностями.

## Чек-лист качества кода

Перед отметкой работы как завершённой:

- [ ] Код читаемый, имена осмысленные
- [ ] Функции маленькие (< 50 строк)
- [ ] Файлы сфокусированные (< 800 строк)
- [ ] Нет глубокой вложенности (> 4 уровней)
- [ ] Корректная обработка ошибок
- [ ] Нет захардкоженных значений (использовать константы или конфиг)
- [ ] Нет мутаций (используются immutable-паттерны)
