# Рабочий процесс разработки

> Этот файл расширяет `git-workflow.md` полным процессом разработки фичи, который происходит до git-операций.

Workflow реализации фичи описывает конвейер разработки: исследование, планирование, TDD, ревью кода, затем коммит в git. Полный цикл TT3Dato: `plan -> test -> implement -> review -> verify -> remember -> improve` (Конституция, раздел 15).

## Workflow реализации фичи

0. **Исследование и переиспользование** _(обязательно перед любой новой реализацией)_
   - **Сначала поиск кода на GitHub:** использовать `gh search repos` и `gh search code`, чтобы найти существующие реализации, шаблоны и паттерны до написания чего-либо нового.
   - **Вторым — документация библиотек:** использовать документацию поставщика, чтобы подтвердить поведение API, использование пакетов и детали версий до реализации.
   - **Веб-поиск только когда первых двух недостаточно:** использовать веб-поиск для широкого исследования после GitHub-поиска и первичной документации.
   - **Проверять реестры пакетов:** искать в npm, PyPI, crates.io и других реестрах до написания утилитарного кода. Предпочитать проверенные библиотеки самодельным решениям.
   - **Искать адаптируемые реализации:** искать open-source проекты, решающие 80%+ проблемы, которые можно форкнуть, портировать или обернуть.
   - Предпочитать заимствование или портирование проверенного подхода написанию кода с нуля, когда это удовлетворяет требованию (Конституция, раздел 2 «НЕ ИЗОБРЕТАТЬ ВЕЛОСИПЕД»).

1. **Сначала план**
   - Использовать агента `planner` для создания плана реализации.
   - Создавать планировочные документы до кодирования: PRD, архитектура, system_design, tech_doc, task_list.
   - Определить зависимости и риски.
   - Разбить на фазы.

2. **TDD-подход**
   - Использовать агента `tdd-guide`.
   - Сначала писать тесты (RED).
   - Реализовать, чтобы тесты проходили (GREEN).
   - Рефакторинг (IMPROVE).
   - Подтвердить покрытие 80%+.

3. **Ревью кода**
   - Использовать агента `code-reviewer` сразу после написания кода.
   - Исправить проблемы CRITICAL и HIGH.
   - Исправить проблемы MEDIUM, когда возможно.

4. **Коммит и push**
   - Детальные сообщения коммитов.
   - Формат conventional commits.
   - См. `git-workflow.md` для формата сообщений и процесса PR.

5. **Предварительные проверки перед ревью**
   - Подтвердить, что все автоматические проверки (CI/CD) проходят.
   - Разрешить конфликты слияния.
   - Убедиться, что ветка обновлена до состояния целевой ветки.
   - Запрашивать ревью только после прохождения этих проверок.

## Evidence trail

Каждый результат сопровождается «следом доказательств»: план, падающий тест, прошедший тест, находки ревью, финальная проверка. Процессные логи — в `Logs/`, детерминированные проверки — в `Tests/`. См. `Logs/README.md` и `Tests/README.md`.
